# Flexova — موديول المبيعات + الفاتورة/الإيصال الإلكتروني (Sales & ETA UI/UX)

> الطبقة 2 — **ثاني موديول في النواة**، وهو **قلب قيمة الامتثال (الـ wedge)** كما في تحليل السوق: العميل بيدخل عشان ETA، وبعدها نوسّع.
> الإصدار: 1.0 — مايو 2026
> يستند إلى: `Project Brief` (القسم 3) · `Market Research` (القسمان 2 و7 — ETA كمحرّك ومتطلب نواة) · `Design Foundations` (الطبقة 1) · `Inventory UIUX` (الطبقة 2 — مصدر الصنف/الضريبة/كود EGS/الوحدات).
> **قاعدة:** يستهلك أسس التصميم وموديول المخزون ولا يعيد تعريفهما.
> **ملاحظة دقّة:** الأرقام التنظيمية (نوافذ الإلغاء/الرفض، عدد الحقول الإلزامية، تعداد الحالات الدقيق) تتبع **الإصدار الحالي من ETA SDK** ويُؤكَّد عليها في مرحلة البناء التقني (نقطة مفتوحة معروفة في الـ Brief).

---

## 0) النطاق والحدود (Scope & Boundaries)

### 0.1 ما يغطيه
عروض الأسعار، فواتير البيع، المرتجعات (إشعار دائن)، إشعار مدين، سندات التحصيل، وطبقة **ETA** كاملة: e-invoice (B2B) + e-receipt (B2C)، التوقيع/الختم، الإرسال والحالات، الرفض وإعادة الإرسال، الإلغاء والتعديل القانوني، ومركز الامتثال.

### 0.2 ما لا يغطيه (يُبنى فوقه)
- **واجهة POS** الكاملة (شبكة المنتجات، الدُرج، الورديات) → قطاع Retail لاحقاً — **لكن منطق e-receipt والتوقيع والمزامنة المُعرَّف هنا مشترك ويُعاد استخدامه**.
- الفوترة الدورية/الاشتراكات → الخدمات لاحقاً.
- كسور الكمية المتدرّجة (quantity breaks) → تحسين جملة لاحق. (قوائم الأسعار نفسها **ضمن v1** وتُجلب من المخزون 2.2.1.)

### 0.3 العلاقة بباقي الموديولات
| الموديول | العلاقة |
|---|---|
| المخزون | الفاتورة تستهلك الصنف (السعر/الوحدة/**نوع الضريبة**/**كود EGS-GS1**) وتولّد حركة **منصرف**. نقص بيانات ETA على الصنف يُحسَم **هنا** (منع الإرسال). |
| العملاء (CRM) | بيانات المشتري + **الرقم الضريبي (TRN)** + UIN؛ تحديد B2B/B2C. |
| الحسابات | سند التحصيل يغذّي الخزينة/البنك؛ الفاتورة تولّد القيد المحاسبي (في موديول الحسابات). |
| الصلاحيات | من يُصدر/يُلغي/يُرسل لـ ETA محكوم بالدور والفرع. |

## 1) خريطة الموديول (Module Map)

```
      عرض سعر (Quotation) ── تحويل ──▶ فاتورة بيع (Sales Invoice) ──────────▶ طبقة ETA
                                          │ يخصم        │ يربط بـ        ┌────────────────────────────┐
                                          ▼             ▼                │ النوع: e-invoice (B2B)       │
                                  المخزون (منصرف)   العميل/CRM           │       e-receipt  (B2C)       │
                                          │          (TRN/UIN)           │ توقيع: e-seal / X.509        │
                                          ▼                              │ UUID + الحالة (Valid/Reject) │
                                  سند تحصيل ◀── الحسابات (خزينة/قيد)      └────────────┬───────────────┘
                                          │                                           │
                       مرتجع/إشعار دائن (Credit Note) ─ مرتبط بالأصل ─────────▶ إشعار ETA مرتبط
                       إشعار مدين (Debit Note) ─────── مرتبط بالأصل ─────────▶ إشعار ETA مرتبط
```

**القاعدة الذهبية للموديول:** الفاتورة المقبولة من ETA **لا تُحذف ولا تُعدَّل** — تُصحَّح بإشعار دائن/مدين أو تُلغى خلال المهلة القانونية. الواجهة تفرض ذلك بصرياً ومنطقياً (ثقة مرئية).

## 2) الكيانات والـ Data Model الظاهر للمستخدم

### 2.1 فاتورة البيع (Sales Invoice) — الكيان المحوري
**الرأس (Header):**
| الحقل | ملاحظات |
|---|---|
| رقم الفاتورة (داخلي) | تسلسل قابل للضبط (انظر نقطة مفتوحة). |
| نوع المستند ETA | `e-invoice (B2B)` / `e-receipt (B2C)` — يُحدَّد آلياً من نوع المشتري مع override (3 و نقطة مفتوحة). |
| ✱ العميل/المشتري | من CRM أو "عميل نقدي". B2B يتطلب **TRN** (9 أرقام) + UIN؛ B2C مبسّط (الرقم القومي فوق الحد القانوني فقط). |
| ✱ التاريخ | تاريخ الإصدار. |
| ✱ المخزن | مصدر الخصم (افتراضي حسب الفرع/المستخدم). |
| الفرع | للعميل متعدد الفروع. |
| طريقة الدفع | نقدي / آجل / تحويل / محفظة / Fawry. |
| ملاحظات | اختياري. |

**الأسطر (Lines):**
`الصنف · الوصف · الكمية · الوحدة (ETA unit code) · السعر · خصم السطر · نوع/نسبة الضريبة (T1 VAT… / T2 جدول…) · إجمالي السطر`.
- الصنف يجلب **كود EGS/GS1** ونوع الضريبة من المخزون. سطر بدون كود = حاجز إرسال (5).
- **السعر** يُجلب تلقائياً من **قائمة أسعار العميل** (المخزون 2.2.1) مع **override يدوي للسطر**.

**الإجماليات (Totals):**
`الإجمالي قبل الخصم · الخصم · الوعاء الخاضع · الضريبة (مفصّلة بالنوع) · الإجمالي النهائي`.

**حقول ETA (تظهر بعد الإصدار):**
`UUID · Long ID · حالة ETA · تاريخ/وقت القبول · رابط/QR · تقرير التحقق (Validation Report)`.

### 2.2 عرض السعر (Quotation)
نفس بنية الفاتورة بدون أثر مخزني أو ETA. حالة: `مسودة/مرسَل/مقبول/مرفوض/منتهي`. **زر "تحويل لفاتورة"**.

### 2.3 إشعار دائن / مرتجع (Credit Note)
مرتبط بفاتورة أصل، أسطر مرتجعة (كل/جزء)، **سبب**. يولّد حركة **وارد** للمخزون (رجوع البضاعة) + إشعار ETA مرتبط بالأصل. لا يتجاوز قيمة الأصل.

### 2.4 إشعار مدين (Debit Note)
زيادة على فاتورة أصل (فرق سعر/رسوم)، مرتبط ومُرسَل لـ ETA.

### 2.5 سند التحصيل (Payment Receipt)
> تمييز مهم: **سند التحصيل** مستند داخلي يسجّل دفعة مقابل فاتورة (نقدي/جزئي). أما **الإيصال الإلكتروني (e-receipt)** فهو مستند ETA الضريبي للـ B2C — مختلفان ولا يُخلطان في الواجهة.
حقول: الفاتورة/العميل، المبلغ، طريقة الدفع، الخزينة/البنك، التاريخ. يدعم **تحصيل جزئي** ومتعدد.

### 2.6 مستند ETA (ملتصق بالفاتورة/الإشعار)
`النوع (invoice/credit/debit) · القناة (e-invoice/e-receipt) · UUID · الحالة · الطوابع الزمنية · الأخطاء (لو رفض) · التوقيع المستخدم · البيئة (sandbox/prod)`.

### 2.7 إعدادات ETA على مستوى العميل (Tenant Settings)
الرقم الضريبي للمنشأة، نشاطها، **الختم/الشهادة (e-seal / X.509 عبر HSM أو USB token)**، **بيئة (sandbox ↔ production)**، نمط الترقيم، سلوك الإرسال (لحظي/طابور). تمهّد لها شاشة 4.8.

## 3) تدفقات المستخدم (User Flows)

### 3.1 فاتورة بيع آجلة (B2B → e-invoice)
اختيار عميل (TRN) → إضافة أصناف (بحث/باركود) → خصم/ضريبة آلية → **مراجعة جاهزية ETA** (لوحة جانبية تبيّن الناقص) → **إصدار وإرسال** → استلام UUID + حالة → طباعة/مشاركة.

### 3.2 بيع نقدي سريع (B2C → e-receipt)
عميل نقدي → أصناف → **تحصيل** → إصدار e-receipt → طباعة/QR للعميل. (نفس المنطق يُغلَّف لاحقاً في POS.)

### 3.3 مرتجع
فتح الفاتورة المقبولة → "إنشاء مرتجع/إشعار دائن" → اختيار الأسطر/الكميات + السبب → إصدار → وارد للمخزون + إشعار ETA مرتبط.

### 3.4 معالجة رفض ETA
الفاتورة تظهر **مرفوضة** بسبب مفهوم بالعامية (مثلاً: "الرقم الضريبي للعميل غير صحيح" بدل Error 422) → زر **"صحّح وأعد الإرسال"** يفتح الحقل الناقص مباشرة → إعادة إرسال.

### 3.5 الإلغاء/التعديل بعد القبول
لا "تعديل" لفاتورة مقبولة. خياران فقط: **إلغاء** (خلال المهلة القانونية، B2B بموافقة المشتري) أو **إشعار دائن/مدين**. الواجهة تخفي زر التعديل وتعرض المسارين الصحيحين.

### 3.6 Offline (أولوية)
الفاتورة تُنشأ وتُطبع وتُسلَّم بدون نت، وتدخل **طابور إرسال ETA**، وتُزامَن عند عودة الاتصال. حالة كل مستند: `محلي / قيد الإرسال / مقبول / مرفوض`.
> تنبيه تصميمي: e-receipt يتطلب إرساً شبه لحظي ضمن نافذة المنظومة — فالمزامنة المؤجّلة لازم تحترم النافذة، والواجهة تنبّه لو مستند قارب تجاوزها.

## 4) الشاشات (Screens)

### 4.1 قائمة الفواتير (Invoices List)
- إجراءات: `+ فاتورة جديدة` · استيراد/تصدير · طباعة.
- **فلترة مزدوجة حاسمة:** فلتر **حالة الدفع** + فلتر **حالة ETA** (منفصلان — انظر 5).
- أعمدة: `رقم · التاريخ · العميل · الإجمالي · حالة الدفع (Pill) · حالة ETA (Pill) · إجراءات`. أرقام `tabular-nums`، نمط compact متاح.
- إجراء صف: عرض · طباعة · مرتجع · إعادة إرسال (لو مرفوضة) · إلغاء.

### 4.2 محرّر الفاتورة (Invoice Editor) — الشاشة المركزية
تخطيط 3 مناطق:
1. **رأس** (عميل/تاريخ/مخزن/نوع المستند/طريقة الدفع).
2. **شبكة أسطر** سريعة: إضافة بالبحث أو **مسح باركود متتابع**، إدخال بالكيبورد بالكامل (وصولية §9 من الأسس)، حساب الضريبة والإجماليات لحظياً.
3. **لوحة جانبية للإجماليات + جاهزية ETA:** تعرض الناقص بوضوح (صنف بلا كود EGS، TRN ناقص، ختم غير مهيّأ…) وتُعطّل زر "إصدار وإرسال" مع توضيح السبب.
- أزرار: `حفظ كمسودة` (دائماً متاح) · `إصدار وإرسال لـ ETA` (مشروط بالجاهزية).

### 4.3 شاشة الفاتورة المُصدَرة (Issued Invoice)
عرض رسمي + **UUID + QR + حالة ETA** بارزة. إجراءات: طباعة PDF (عربي/إنجليزي)، مشاركة (واتساب/بريد)، تحميل، إنشاء مرتجع، إلغاء (مشروط)، تحصيل. حالة مرفوضة تعرض السبب + "صحّح وأعد الإرسال".

### 4.4 المرتجعات والإشعارات (Credit / Debit Notes)
محرّر مشابه مربوط بالأصل، حقل **سبب** إلزامي، يعرض أثر المخزون والقيمة المتبقية القابلة للإشعار.

### 4.5 عروض الأسعار (Quotations)
قائمة + محرّر + زر "تحويل لفاتورة". لا أثر مخزني/ضريبي قبل التحويل.

### 4.6 سند التحصيل (Payment Receipt)
من فاتورة أو مستقل، يدعم جزئي/متعدد، يحدّث **حالة الدفع** للفاتورة.

### 4.7 مركز ETA (Compliance & Sync Hub) — شاشة "ثقة مرئية"
لوحة مركزية: المستندات حسب حالة ETA (قيد الإرسال / مرفوضة / غير مُرسَلة / مقبولة)، إعادة إرسال جماعية، و**KPIs**: نسبة القبول (acceptance rate)، أكثر أسباب الرفض، مستندات قاربت نافذة الإرسال. مؤشّر offline دائم.

### 4.8 إعدادات ETA (Tenant)
الرقم الضريبي، الختم/الشهادة، **تبديل sandbox/production**، نمط الترقيم، سلوك الإرسال، أنواع الضرائب المفعّلة. **معالج إعداد (wizard)** أولي يربط الحساب ويختبر على sandbox قبل الإنتاج.

## 5) الحالات (States) — المحور الأهم: بُعدان متعامدان

> **مبدأ "الثقة المرئية" مجسَّداً:** حالة الدفع وحالة ETA **مستقلتان** ولا تُدمَجان. فاتورة قد تكون *مدفوعة* لكن *مرفوضة من ETA*.

**أ) حالة الدفع (Pills):** `مدفوعة` (success) · `مدفوعة جزئياً` (warning) · `آجلة` (warning) · `مرتجعة` (محايد).

**ب) حالة ETA (Pills):** `مسودة` · `غير مُرسَلة` · `قيد الإرسال` · `قيد الاعتماد` (B2B pre-clearance، قبل قبول ETA) · `مقبولة Valid` (success) · `مرفوضة Rejected` (danger) · `ملغاة` (محايد) · `رُفضت من المشتري` (danger, خلال 72 ساعة).

**الحالات الخمس لكل شاشة بيانات** (تحميل/فارغ/خطأ/بحث فارغ/offline) كما في الأسس §7، مع:
- **رفض ETA:** سبب بالعامية + الحقل المسبّب + إجراء تصحيح. ممنوع عرض أكواد تقنية للمستخدم النهائي.
- **Offline:** الإصدار والطباعة يعملان؛ الإرسال في طابور؛ حالة `محلي/قيد الإرسال/مقبول/مرفوض` + تنبيه اقتراب نافذة الإرسال.
- **منع الإرسال (قرار هذا الموديول):** الحفظ كمسودة دائماً متاح؛ **الإرسال** ممنوع عند نقص (كود EGS/GS1، نوع ضريبة، TRN للـ B2B، ختم غير مهيّأ) — مع لوحة جاهزية صريحة (4.2).

## 6) التكاملات (Integrations)
- **ETA SDK:** توقيع e-seal/X.509 (HSM/USB token)، بيئة sandbox/prod، أكواد **EGS/GS1**، **أكواد الوحدات**، أنواع الضرائب (T1 VAT 14% وغيرها)، توليد/تخزين **UUID + QR + Validation Report**.
- **التحقق من المشتري:** استدعاء التحقق من **TRN/UIN** قبل اعتبار العملية B2B.
- **المخزون / CRM / الحسابات:** خصم، بيانات المشتري، التحصيل والقيد.
- **الدفع المحلي:** Fawry/محافظ/تحويل لربط التحصيل (يخدم مشكلة التحصيل في تحليل السوق).
- **الطباعة/المشاركة:** PDF رسمي ثنائي اللغة + QR + واتساب.

## 7) RTL والتعريب
- المستند الرسمي ثنائي اللغة (عربي رئيسي/إنجليزي مرآة)؛ الأرقام غربية + `tabular-nums`؛ العملة `ج.م` بعد الرقم؛ الضريبة والإجماليات بمحاذاة منطقية.
- الرقم الضريبي/UUID/الأكواد تُعرض LTR ضمن سياق RTL (bidi مُختبَر).

## 8) الأداء
- شبكة أسطر تتحمّل عشرات الأسطر بإدخال لحظي بلا تهنيج؛ قائمة فواتير كبيرة بـ server-side pagination؛ طابور إرسال ETA لا يحجب الواجهة (غير متزامن، مع مؤشّر تقدّم).

## 9) القرارات (كانت نقاطاً مفتوحة) — كلها محسومة لـ v1

**محسومة لـ v1:**
1. ~~تحديد e-invoice مقابل e-receipt~~ — ✅ **آلياً** من وجود TRN صالح للمشتري (موجود ⇒ B2B/e-invoice، غائب/عميل نقدي ⇒ B2C/e-receipt) + **override يدوي** عند الحاجة.
2. ~~سلوك الإرسال~~ — ✅ **Hybrid بإيقاعين حسب القناة** (مُحدَّث بعد تحديث ETA يونيو 2026): **B2B/e-invoice = near-real-time clearance** — لا تُعرض كـ"صالحة نهائياً" قبل قبول ETA (حالة `قيد الاعتماد`)؛ **B2C/e-receipt = طابور ضمن النافذة (24–72 ساعة)** مع إصدار + طباعة فوراً وإرسال خلفي. offline ⇒ طابور + **تنبيه أحمر** عند اقتراب النافذة. لا batch مجدول. نفس المسار يُعاد في POS.
3. ~~ترقيم الفواتير~~ — ✅ **تسلسل لكل فرع** (sequence per branch)، مع بادئة فرع لتجنّب التعارض. (يُراعى في طابور الإرسال والمزامنة offline.)
4. ~~العملات المتعددة~~ — ✅ **جنيه فقط في v1**؛ تعدّد العملات يُؤجَّل لمسار الاستيراد/التصدير.
5. ~~الدفعات المقدّمة/الفوترة على دفعات~~ — ✅ **داخل النواة** (down payment + فوترة على دفعات مدعومة في الفاتورة/سند التحصيل).
6. ~~قالب الطباعة + QR~~ — ✅ **قالب قياسي ثنائي اللغة بالحقول الإلزامية مقفولة** (بيانات البائع/المشتري، أكواد الأصناف، تفصيل الضريبة، الإجمالي، UUID، QR) + **تخصيص محدود per-tenant** (لوجو، اسم تجاري، ألوان الثيم، فوتر/ملاحظات) بدون مساس بالإلزامي. مقاسان: A4 و**رول 80mm** (إيصال حراري لـ POS).
7. ~~Sandbox افتراضي~~ — ✅ العميل الجديد يبدأ في **sandbox** تلقائياً مع **مؤشّر "وضع تجربة" دائم**، والتحويل لـ **production** خطوة واعية بتأكيد صريح في إعدادات ETA (4.8).

## 10) ما يبني عليه هذا المستند لاحقاً
- **التالي:** موديول **المشتريات** (وارد + فواتير الموردين، يكمّل دورة المخزون).
- **لاحقاً:** الحسابات (القيد والخزينة تستهلك التحصيل والفواتير).
- **طبقة Retail/POS:** تعيد استخدام منطق e-receipt/التوقيع/المزامنة هنا داخل واجهة POS لمسية offline-first.
